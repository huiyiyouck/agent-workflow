## 一、定位陈述（指挥官 2026-07-23 口头确认）

**目标形态：给一个目标，团队自动按目标做完，输出交付物（goal in → deliverable out）；生态层面，项目与项目之间的协调也自动化。**

即组织法则三预留的「下一次定位升级：全自动（决策权下放）」。本 BCR 将其从预留位转为正式演进主线，并确立分级实施路线。

## 二、动机（用自身数据，非外部方法论倒推）

- 现行框架 `docs/baseline/` 中「用户确认 / Owner / 停等 / 先问 / 询问」关键词命中 **78 行**（密度最高：mechanisms 14 / cross-project-collaboration 14 / multi-agent-workflow 12 / runtime 8）。**【已实测替换（0.2 台账，2026-07-26，Owner 拍板通过）】**逐条定性结果：真停等 **47 落点 / 约 33 条规则**（31 行为定位陈述等非停等语义，剔除），其中 **L1 需砍仅 6 条规则**（全部落在 L1 方案 S1-S4 改写面内）；L0 分仓基线——workboard 确认类 **≈11-12 次/迭代**（其中 S1-S4 范畴 ≈7 次）、xiaobao **≈17-19 次/迭代**（Owner 方向性决策密度更高，属 A 组不可砍）。台账见 `docs/progress/ad-hoc/2026-07-25-bcr-015-stop-point-ledger-l0-baseline.md`。**半自动形态下生产效率的瓶颈是 Owner 停等而非执行速度——此定性判断不依赖上述具体数字**（流水线每阶段定稿、关闭、收尾均设人工确认是结构事实）。
- 框架内已存在目标形态的微缩模型：`role-developer-detail.md` + `subagents/` 的「派发 → worktree 隔离 → 自动验收三项 → 有限重试 → 兜底接管」闭环（作用域限实现阶段前后端子 agent）。本升级本质是把该闭环逐级放大：实现阶段 → 全迭代 → 跨项目。
- 直接并行化不可行（阿姆达尔定律）：只要验收与决策全集中于 Owner 一人，并行 N 条迭代 = Owner 队列积压 N 倍。故必须**先下放决策权、再谈并行**，且分级进行。

## 三之二、决策权分类（判据 + 两组清单）

> 本节是**各级「Owner 保留」列的唯一真源**，也是阶段 0.2 停等点台账逐条定性的判据来源。原「L1 行保留项」与「永久保留四项」两处清单口径不一致（R3 裁决 / 变更三档定性归属相反），已按下列判据重切合并。

### 判据（单一、可测，用于 78 处台账逐条定性）

> **问：这个决策改变的是「什么算做好了」，还是「怎么把它做好」？**
>
> - 改变**「什么算做好了」**（目标、范围、验收含义、对外承诺）→ **A 组 · 永久保留**
> - 只决定**「怎么把它做好」**（顺序、实现、调度、重试、流程推进）→ **B 组 · 分级下放**
> - **「做完了没有」的判定** → 判定权下放给机器，**否决权（打回）留 A 组**
>
> **存疑时向上取整**：判不准属 A 还是 B，一律按 A 处理（升级 Owner）。这是 `multi-agent-workflow.md §11.2`「不能把重大变更伪装成轻量变更」的机制化——原文只有禁令没有机制，本判据补上默认方向。

## 四、留痕对偶原则（指挥官 2026-07-23 增补要求，宪法层原则）

**砍停等、不砍留痕；介入减少、留痕增厚。** 自动化削减的是 Owner 现场确认次数，不是文档输出；抽检权的前提是详尽留痕，故：

1. **对偶律**：每下放一项决策权，必须同步新增对应留痕义务——决策由谁（哪个门禁/agent）做出、依据什么判据、证据链接、为何如此选择。**不留痕的决策权不得下放。**
2. **新增四类自动留痕**（由编排/门禁强制产出，非靠会话自觉）：阶段执行记录（含门禁项与结果）、决策留痕（方案/备选/理由）、失败与重试史、验收证据链（验收标准 ↔ 测试逐条对应）。
3. **双层留痕结构**：详尽轨迹层（append-only 全量，供排查深挖）+ 蒸馏摘要层（Owner 抽查入口：状态/异常点/待裁决项）。沿用现有 current/summary/archive 分层；**写得多、读得少**——Agent 启动仍只读摘要层，不违上下文税原则。
4. **现有文档产物一个不减**：vX.Y.md、INDEX.md、角色日志、Review 记录、ad-hoc 全保留，执笔从"人提醒"改为"流程强制"。

## 五、本 BCR 的实施范围

- **本次只落 L1**：验收可执行化 + CI 机器门禁 + 阶段间免确认改造 + 留痕对偶的 L1 部分。L2/L3 仅立方向，届时各自另走 BCR。
- **修改面（L1，评估阶段细化）**：根 CLAUDE.md 组织法则三表述；baseline 中阶段定稿/Review 通过的停等规则（台账中属 L1 范围的子集，规模待 0.2 实测）；PRD 模板（验收标准可执行化字段）；迭代关闭检查（验收证据链核对）；**CI 基建从零搭建 + CI 门禁脚本**（四仓现均无 `.github/workflows`）；**生产发布放行显式红线**（A4 现无独立条文，仅间接绑于 A3，见 §三之二）。
- **L1 试点仓 = `niuma-cheng-workboard`（指挥官 2026-07-25 拍定）**：迭代节奏约 13 天/迭代（三仓最稳，能在 4-6 周内攒够试运行样本）、已有 14 个测试文件与 `node --test`（G3 当天可用、CI 成本最低）、解析侧度量载体与试点同仓（自我验证）、内部工具出错代价可控。**首批只搭该仓 CI**；真源仓同期加轻量 workflow（跑 `measure-context.sh` + 双入口 diff）。第二试点 `niuma-cheng-ai`（待其恢复迭代，覆盖纯后端高自动化率形态）；`niuma-cheng-xiaobao` 最后进，**其测试基建补齐列为 L1 范围外的独立前置任务**（主产品 v0.6 零测试本属存量风险，非 L1 强加）。
- **配套指标调整**：因 workboard 前端占比高，§四「人工抽检占比 >50% 否决」改为**分层**——后端/解析层/数据层自动化率 100%（硬指标），界面层允许「构建 + 截图 + 人工抽检」只记录不否决。避免「L1 机制是否有效」与「该项目天生难自动化」两件事互相污染数据。
- **明确不做**：Skills 化（v1 方案**已废弃**，L2 编排落地后按「缺什么取什么」重估调研存档）；4 指标人工填报度量（按 BCR-013 判例，能解析侧算的走解析侧）；跨项目红线改写（留 L3）。
