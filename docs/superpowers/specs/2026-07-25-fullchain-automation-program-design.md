## 一、升级程序的三条元规则（升级自己也要守规矩）

1. **升级本身按批次走**：每个交付批次（下称 **U 批次**——只是交付批次，**不是标准迭代实例，不套 PRD/设计/Review 阶段门禁**；真源仓维护身份见 `agent-workflow/CLAUDE.md` SOURCE-REPO-ONLY 段）都有明确范围、产出、回归验证、Owner 拍板点，落 ROADMAP 游标（延续 P 系列编号），可追溯可回滚。不搞一次性大爆炸改造。
2. **一次 BCR 只锁一级**：本次 BCR（预计 BCR-014）只授权 L1 的落地；L2、L3 在前级晋级评审通过后**各自另立 BCR**。这样每级都有独立的拍板点，方向错了损失止于一级。
3. **升级过程本身留痕对偶**：每个 U 批次的方案都过「Owner 拍板 + 独立对抗式 review 会话」双关（固化自前案 `2026-07-22-trae-skills-upgrade-design-deprecated.md` 的对抗式 Review 模式，该案 Review 记录见其文末）。**review 席位说明**：评审会话与起草会话同为参谋长席位（不同会话），这是一人公司条件下对「核心产出 ≥2 独立 Review 方」的最优近似；为守独立性，review 会话**只读真源、只准反驳与举证，不得替起草方提案或改写正文**（Review 结论一律追加进被评审文档自身）。每次真源变更走 PR 合 main（回应 P14 时 Owner 的观察项①）；每轮回流报备 + 回执 + BCR 池回填。

## 二、整体链路：从现在到 L3 的完整走法

```text
阶段0 程序启动（BCR 登记 + 评估）
   └→ L1 建设（真源侧 3 个 U 批次）
        └→ L1 试运行（下游真实迭代 ×2-3，采数据）
             └→ L1 晋级评审（Owner 抽检 + 数据核对）——达标才继续
                  └→ L2 BCR（另立）→ L2 建设 → L2 试运行 → L2 晋级评审
                       └→ L3 BCR（另立）→ …… → 终态
```

|---|---|---|
| 0.1 BCR-014 登记 | coordination `REQUESTS.md` BCR 池新行（状态：已提报→评估中） | 指挥官过目草案后授权登记 |
| 0.2 停等点台账 + 两项实测 | 真源 `docs/progress/ad-hoc/`，三个产出：① **真实停等点计数**——以 78 行关键词命中为筛查底表，逐条判定「是否真停等」（命中行含定位陈述/建仓说明等非停等语义，真实 N 很可能远小于 78）；② **L0 真实基线（按仓分别算，不合并）**——从 xiaobao/workboard 已完成迭代的 git log + 迭代记录 + 角色日志反推实际确认次数，分仓存值：晋级时试点仓与**自身**基线比（口径同源才可比）；其余仓基线供各自进入试点时用，且分仓数据能揭示哪类项目自动化收益高，对 L2 有参考价值；③ 分类台账本体——按 **BCR §三之二判据**（A/B 组 + 存疑向上取整）逐条定性 L1/L2/L3/永久保留，每条注真源位置与理由。**晋级绝对阈值待 ①② 实测数出来后定** | 台账是 L1 改动范围的唯一依据；**Owner 逐类拍板 + 敏感条目单列逐条拍**——凡命中 ⑴ 原文标 `[P0]` ⑵ 涉跨仓/跨项目写入 ⑶ 涉删除等不可逆动作 ⑷ 一句话捆绑多项权力 ⑸ 属异常升级路径（「无法判断时报 Owner」类）任一者，从类里拎出逐条拍（按真源实况估约 5-10 条，成本可控） |
| 0.3 L1 方案定稿 | `L1升级方案` 按台账修订 → 定稿 | Owner 拍板 + 独立 review 会话对抗审 |

### L1 建设 · 真源侧 3 个 U 批次（预计对应 ROADMAP P15）

| U 批次 | 范围 | 完成条件 |
|---|---|---|
| **U1 模板与留痕改造** | PRD 模板补「验收标准→验证命令」映射；迭代记录模板补「阶段执行记录 / 验收证据链 / 异常升级记录」三个小节；关闭检查补证据链核对项 | 模板改动全部有对应回归用例；双入口一致；measure 复测不回归 |
| **U2 CI 机器门禁** | **首批只搭试点仓 workboard 的 CI**（G1-G5 五项门禁，见 L1 方案 §二块 2；四仓现均无 `.github/workflows`，系从零搭建）+ 真源仓轻量 workflow（`measure-context.sh` + 双入口 diff）；错误输出按「静默通过、只报失败、写给 AI 的指导」三纪律 | 真源仓 + workboard 绿灯跑通；**G1/G4 对存量迭代记录静态回放误报清零；G2/G3/G5 走 fixture 正负样本全部按预期**（G2/G3 依赖 U1 新增字段，存量数据回放不了） |
| **U3 免确认规则改写** | 按台账把 L1 子集的停等规则改写为「门禁通过即进、异常才停」，**免确认条文内置降级条款**（约定名门禁 `l1-gates.yml` **未返回绿灯**的仓维持 Owner 确认旧行为——判据是门禁结论而非仓的配置状态，见 L1 方案 §四）；同步改 standard-iteration-quick / multi-agent-workflow §7（:115 **拆句**）/ mechanisms 正文 + 总纲(:7) + 机制总表(:26-29)（详见 L1 方案 §二块 3 改写面） | 回归用例全过（含负向：门禁红灯时**不得**自动进下一阶段、打回后**不得**静默重放行）；保留项（**BCR §三之二 A 组全部 + B 组 L1 保留项**）逐条确认未被误关 |

每个 U 批次的固定收尾动作：回归用例 → PR 合 main → `sync-downstream.sh` **三仓同时回流**（新规则含降级条款，`l1-gates` 未返回绿灯的仓行为不变——不产生多框架版本并行、不违职责④「改完顺手回流」、无 `.workflow-version` 漂移）→ BCR 池回填 → ROADMAP 游标更新。

### L1 试运行 · 下游侧验证（不新增 U 批次，用真实业务迭代当测试场）

1. 试点仓 = **`niuma-cheng-workboard`**（指挥官 2026-07-25 拍定，四条理由见 L1 方案 Review 记录「试点仓推荐」节）：其下一个真实迭代按 L1 新规则跑。第二试点 = ai（待其恢复迭代，覆盖纯后端高自动化率形态）；xiaobao 最后进，且先补测试基建（L1 范围外独立前置任务）。
2. 观测口径（**全部解析侧统计，零人工填报**，遵 BCR-013）：人工介入次数（从会话切换与确认留痕数出）、门禁一次通过率、异常升级次数、抽检发现的漏放数。
3. 试运行判据用**覆盖矩阵**而非纯迭代数（样本量不是主要矛盾，覆盖面才是）：至少覆盖 ⑴ 一次含界面变更的迭代 ⑵ 一次触发 Change Note 或阶段回环的迭代 ⑶ 一次门禁红灯被正确拦下的实例（可人为注入）。矩阵集齐前不进晋级评审，预计 2-3 个迭代可集齐。期间发现的规则问题按正常 BCR 流程提报（不现场改）。

### L1 晋级评审（进入 L2 的唯一入口）

- **数据关**：**试点仓与其自身 L0 基线比**（workboard 的 L1 表现 ÷ workboard 的 L0 基线，口径同源才可比，不用混合基线），确认类介入**下降 ≥70%**（相对指标，抗基线误差；分子只计「本应被 L1 砍掉却仍发生的确认」，A/B 组保留项确认单独计数不入分子，口径见 L1 方案 §一；绝对阈值待 0.2 实测后定）+ 覆盖矩阵三项集齐。**度量只统计运行于完整门禁模式（`l1-gates` 绿灯）的迭代；降级模式迭代单独记录、不计入晋级判据**——降级留痕行（L1 方案留痕义务第 5 条）使此筛选自动成立，无需额外机制。
- **注入关（有效性验证）**：从三下游历史上**真实被打回 / 真实出过问题的迭代**里挑 1-2 个，用新门禁 + 新留痕体系回放——能拦下、或至少在留痕中暴露，才算门禁有效。（抽检验证不了「留痕正确」只能验证「留痕可读」，且一次抽查命中漏放的概率很低；注入式回放数据现成、成本低、判据硬。）
- **留痕关（可读性验收）**：Owner 沿新留痕体系实际回溯一次全链路（入口 = 迭代记录三小节，从目标到交付物沿验收证据链走通），确认「查得动、查得全」——这是留痕对偶原则的验收。
- 三关全过 → 参谋长代拟 L2 BCR；不通过 → 修 L1 或降级回退（见 §四）。

### L2 / L3 · 只立方向（届时各自 BCR 再细化）

- **L2 关键工程**：编排层 v1（把 `role-developer-detail` 微缩闭环放大到全迭代——开会话/派角色/传上下文/失败重试/兜底升级）+ 状态真源程序化（vX.Y/INDEX 程序读写）。**此时才重估调研存档**：worktree 并发隔离、信号降噪测试脚本、控制平面设计、Skills 化（按「缺什么取什么」）。
- **L3 关键工程**：跨项目信道程序化（人工公告板红线的受控改写，宪法层，单独拍板）+ 多项目并行编排。
- 每级同样走「建设 → 真实试运行 → 晋级评审」三段,晋级条件已写入 BCR 草案 §三。

## 三、治理节奏（每个 U 批次的固定拍子）

```text
方案（参谋长拟）→ 对抗式 review（独立会话）→ Owner 拍板
   → 真源落地（PR 合 main）→ 回归用例全过
   → 回流三下游（sync 脚本 + 报备回执）→ BCR 池回填 + 游标更新
```

- 参谋长全程只做拟案/执行/回流；每个「→」处的放行权在 Owner（L1 落成前，升级程序自身仍是半自动——用旧规矩造新规矩，不自举越权）。
- 升级期间三下游的业务迭代照常跑，回流窗口选各仓工作区干净时（sync 现有 dirty 拒绝护栏兜底）。

## 四、风险与回滚

| 风险 | 应对 |
|---|---|
| 免确认放行了坏产出 | Owner 抽检走「打回」（已有状态词）；打回即产生一条 corrections + 门禁补强候选——坏放行喂回门禁，形成收紧回路 |
| CI 门禁误报拦真活 | 门禁项全部 fixture 化（正/负样本）；上线前验证分门禁定方式——**G1/G4 静态回放存量迭代记录、G2/G3/G5 走 fixture**（后者依赖 U1 新增字段或稀有状态，存量数据回放不了）；误报按「失败分类」修 lint 不改红线 |
| L1 数据不达标 | 不晋级；按台账把已关停等点逐条回看，可单点恢复（每处改动独立 commit，可 revert + re-sync 精准回滚） |
| 升级拖垮业务节奏 | U 批次与业务迭代不抢会话：真源侧改造不占用下游会话；试运行就是业务迭代本身，无额外成本 |
| CI 基建为零（四仓均无 `.github/workflows`） | U2 首批只搭 workboard 一仓 + 真源轻量 workflow，体量收缩为正常批次；xiaobao 测试基建欠账列为 **L1 范围外独立前置任务**（主产品零测试本属存量风险，非 L1 强加，L1 只是把它显性化） |

## 四之二、回本点（预期管理）

粗算投入：阶段 0（3 步）+ 3 个 U 批次 × 7 步治理拍子 ≈ **24 个 Owner 触点**；粗算回收：试运行期 2-3 个迭代 × 每迭代节省的确认次数（待 0.2 实测，量级约 10+ 次）≈ 20-30 次——**此回收按试点仓单仓计**；其余两仓在降级条款下行为不变、零节省，**生态口径的回本点相应后移**，直至各仓陆续进入门禁模式。**大致到试运行结束前后才回本，建设期体感会比现状更累**——这是一次性投入换持续收益的正常曲线，不是方案失效信号，此节的作用是防中途动摇。L1 晋级后收益持续累积；L2/L3 复用 L1 的门禁与留痕地基，边际投入递减。
