# BCR-014 + BCR-016 合并评估方案（参谋长，2026-08-08）

> 状态：**v1 待指挥官过目**。过目通过后按 §4 落地真源并回流。
> 授权依据：指挥官 2026-08-08 授权参谋长合并评估落地（会话拍板）。

## 1. 为什么合并评估

两条提案同型：**现有规则把关键约束放在「执行者自律 / 事后核对」上，实证已失效，都要求换成「事前机制约束」**。

| | BCR-014 | BCR-016 |
|---|---|---|
| 提出方 | workboard · PM（2026-07-13） | ai · DevOps（2026-08-01） |
| 失效的自律 | 「两方独立 Review」默认执行者不会切成 Review 方审自己 | [P0]「push 前贴 `git diff --stat` 核对范围」——人在收尾时倾向快速通过 |
| 实证 | workboard v0.3 R1：PM 同会话切 Architect 审自己刚写的 PRD，Owner 当场拦下 | 同日两起、方向相反（DevOps 卷入 Architect 24 行；PM 反向卷入 DevOps 约 40 行），均已 push 无法改写 |
| 换成的约束 | 切 Review 角色前的**准入检查**（产出方会话拒绝切换） | 提交范围的**事前限定**（禁裸 `git add -A`，只 add 明确文件列表） |

## 2. 评估结论

**两条均采纳**，改动面刻意压到最小（护栏优先、不铺条文，符合 Owner「规则宜精简」取向）。

### BCR-016（改动更小，先说）

1. `docs/baseline/conventions.md`「Git 工作流」结束步骤 1 由提示语升为禁令：
   - 现行：`git add 修改的文件（只 add 本任务归属的文件）`
   - 改为：`git add <明确文件列表>（只 add 本任务归属的文件；多角色共享工作区禁止裸 git add -A / git add .）`
2. 同文件「禁止事项」新增一条：**禁止裸 `git add -A` / `git add .`**；确需批量暂存时，`git diff --cached --stat` 的**每个文件名须逐一匹配本次改动清单**，有任何一个对不上即 reset 重新 add——判据是「清单逐一匹配」，不是「有没有报错」。
3. `docs/regression-cases.md` 补一条回归用例（ai 仓 `a2943e2` / coordination `0cc7510` 双实例）。

不采纳的部分：git hook 级硬拦截。暂存方式（是否经 `-A`）在 git 层不可追溯，hook 无法可靠判定，强上只会误伤；条文 + 回归用例已把判据变成可机械执行的操作（列文件名），性价比最高。将来若再犯，升级方向是「commit 前脚本比对 staged 清单 vs 会话声明清单」，届时另立提案。

### BCR-014

1. 入口 `CLAUDE.md` + `AGENTS.md`「角色切换触发」节，精准触发表后新增**Review 独立性检查**（约 3 行）：
   > 切换目标角色若被指定 Review 某产出，且该产出（全部或部分）产自**本会话**：拒绝切换，回复固定话术提示 Owner 新开会话冷启动做 Review。该检查优先于精准触发的「不反问」规则。
2. `docs/baseline/multi-agent-workflow.md` Review 机制处补一句硬性表述：**Review 方必须是未参与该产出的独立会话**；产出方会话切角色不改变其产出方身份。
3. `docs/regression-cases.md` 补一条回归用例（workboard v0.3 R1 实例：正向=拒绝切换话术，负向=不得因「Owner 亲口说你是架构」就放行）。

残余风险（如实报告）：这仍是入口条文级护栏，靠模型在切换时执行检查，不是 CI 级硬机制。**机器化候选（R1·M1 订正）**：同会话自审有一个无需会话身份的 git 侧可观测特征——**产出与其 Review 结论落在同一个 commit**，git 直接可查、成本近零（与 BCR-013「解析侧探底、零框架税」判例同型）；会话指纹方案并非唯一路径。**判断：条文放在「切换动作发生的唯一入口」，比散布性自律强一个量级，先落这层；机器化（优先同 commit 特征检测）留给 L1 晋级后按需评估。**

### 与 BCR-015 的相互作用（BCR-016 提报方所提）

成立且已覆盖：L1 免确认提高提交频率 → 两条护栏恰好是免确认阶段的前置卫生条件。结论：**两条护栏先于新项目（L1 新首试点）开工落地**，新项目 Bootstrap 即带全量护栏。

|---|---|---|---|---|
| B1 | §4.1 完成条件（外部缺陷，本方案前置） | **真源仓 framework-checks 自 2026-07-27 起持续红，且波及面不止红掉的那一个用例**。根因定位到 `ci/gates/l1-gates.sh:16`：`after_colon() { awk '{i=index($0,"："); print (i? substr($0,i+3) : "")}'; }`——`i+3` 是**按字节**跳过全角冒号（UTF-8 3 字节）。BSD awk（macOS）字节语义 → 取值正确；GNU awk（CI Linux，UTF-8 locale）**字符语义** → `substr(i+3)` 多跳 2 字符、值被截断。实测：`- 最终状态：已完成` 在 macOS 得 `已完成`、Linux 得 `成`。**该函数有 4 个调用点，其中 3 个是 G5 打回闸的输入**（:92 `ov` / :97 `final_val` / :98 `concl_val`）——`- Owner 验收…：打回（UI 不符）` 在 Linux 上取到 `（UI 不符）`，`case *打回*` 不命中，**G5 静默 fail-open**（不报错、不亮红、就是不拦）。故：⑴ `c0dc32a`「U3.2 双逃逸修复收官、试运行放行条件满足」**不成立**（该批修复只在 BSD 语义下成立，且正是它把 CI 从绿变红——7/27 02:35 前有绿 run）；⑵ 全套设计信条是 fail-closed，**门禁脚本自身在解析失败时却 fail-open**，属比单个用例更根本的缺陷类别；⑶ 历轮回执引 workboard 仓绿灯、未看真源自身红灯，属流程漏洞非手误 | **阻塞** | 先修 CI 再落地本方案。修法：`after_colon` 改为不依赖 awk 语义的取值（如 shell 参数展开 `${line#*：}`），并补一条防复发回归用例（同一断言在 BSD/GNU 双语义下须同结果）。属**工具缺陷修理，不动 baseline 规则、不涉任何条文**。另建议排查 `l1-gates.sh` 内其余按字节偏移处理多字节字符的写法 |
| G1 | §2 BCR-016 第 2 条「批量暂存例外通道」 | **例外通道与本提案的诊断自相矛盾**。本方案 §1 认定失效的自律正是「push 前贴 `git diff --stat` 核对范围——人在收尾时倾向快速通过」；而例外通道要求「确需批量暂存时，`git diff --cached --stat` 每个文件名须逐一匹配本次改动清单」——**同一动作、同一时点、同一失效模式**，等于用出问题的那个机制去救它自己。另：§5 保留它的理由「框架自身跑 sync 回流时批量场景真实存在」**被真源实况证伪**——sync 回流的文件集**固定且已知**（`CLAUDE.md` / `AGENTS.md` / `docs/baseline/` / `docs/templates/` / `.workflow-version`），且 `sync-downstream.sh` 步骤 7b（BCR-008 回流护栏）**已在用同一份白名单校验**；清单既然固定，直接写明确路径即可，不需要 `-A` | 高 | **一刀切全禁 `git add -A` / `git add .`，不留例外通道**。回流场景用固定路径列表（可直接取自 sync 脚本白名单）。这样判据从「人逐一比对」变成「命令里根本没有 `-A`」——**可被机器一眼看出，才算换成了事前机制约束** |
